# ARCHITECTURE.md — Native File System Architecture

Version: 1.0

Status: Approved

---

# 1. Purpose

The Native File System layer provides a secure, platform-independent abstraction for all file and directory operations used by OfficeX Desktop.

Applications must never access the operating system file APIs directly.

All file operations must be performed through the File Service exposed by the Shared Runtime.

---

# 2. Design Goals

The File System architecture must be:

* Secure
* Cross-platform
* Offline-first
* Testable
* Modular
* Extensible
* Transaction-aware where practical
* Compatible with large documents

# 4. Responsibilities

The File Service is responsible for:

* Open files
* Save files
* Save As
* Create files
* Delete files
* Rename files
* Move files
* Copy files
* Create folders
* Read metadata
* Monitor file changes
* Export documents
* Import supported formats

# 6. Core Interfaces

The File Service should expose operations conceptually equivalent to:

* OpenDocument
* SaveDocument
* SaveDocumentAs
* CreateDocument
* DeleteDocument
* RenameDocument
* MoveDocument
* CopyDocument
* CreateFolder
* GetMetadata
* ListDirectory
* WatchDirectory
* ExportDocument
* ImportDocument

Applications depend on these interfaces rather than platform-specific implementations.

# 8. File Metadata

Every opened document should expose metadata such as:

* Document ID
* File name
* File path
* Extension
* MIME type
* File size
* Created time
* Modified time
* Last opened time
* Read-only status
* Owner (if available)

Metadata is cached during the editing session.

---

# 9. Open Workflow

Typical document open flow:

```text id="w7dy4n"
User Action

↓

Open Dialog

↓

Validate Path

↓

Read File

↓

Detect Format

↓

Parse Document

↓

Create In-Memory Model

↓

Open Editor
```

If parsing fails, an error is reported without crashing the application.

---

# 10. Save Workflow

Save flow:

```text id="0g4q8v"
Validate Document

↓

Serialize

↓

Write Temporary File

↓

Verify Write

↓

Replace Original File

↓

Update Metadata

↓

Mark Document Clean
```

Using a temporary file before replacing the original reduces the risk of corruption.

---

# 11. Auto Save

The File Service supports configurable automatic saving.

Requirements:

* Periodic save.
* Save only changed documents.
* Preserve previous version until save completes.
* Recover unsaved work after crashes.

The auto-save interval should be configurable by the user.

---

# 12. File Watching

Directory and file watchers detect:

* External modifications.
* File deletion.
* File rename.
* Permission changes.

When conflicts occur, the user should be informed and offered appropriate actions.

---

# 13. Recent Documents

Maintain a list of recently opened documents.

Each entry includes:

* File path
* Display name
* Application
* Last opened time
* Pin status

The list should be stored separately from document content.

---

# 14. Recovery

Recovery information should include:

* Unsaved edits
* Temporary snapshots
* Recovery timestamp
* Original file reference

Recovered data should be presented to the user on the next launch after an abnormal shutdown.

---

# 15. Security

The File Service must:

* Validate paths.
* Restrict access according to user permissions.
* Avoid following unexpected symbolic links unless explicitly supported.
* Sanitize file names generated by the application.
* Protect temporary files.

Renderer processes never receive unrestricted filesystem access.

---

# 16. Performance

Goals:

* Lazy-load large documents where possible.
* Cache frequently accessed metadata.
* Stream large file reads when practical.
* Avoid blocking the main application thread.

---

# 17. Extensibility

New storage providers (for example, cloud storage) should implement the same File Service interfaces without requiring changes to document editors.

---

# 18. Testing

Required tests include:

* File open
* Save
* Save As
* Rename
* Move
* Copy
* Delete
* Metadata
* Recovery
* Auto-save
* External modification detection
* Large file handling

---

# 19. Acceptance Criteria

The Native File System architecture is complete when:

* All document operations use the File Service.
* Applications remain independent of platform-specific file APIs.
* Auto-save and recovery operate correctly.
* File metadata is tracked consistently.
* External file changes are detected.
* Security and validation rules are enforced.
* The architecture supports future storage backends without major redesign.

End of Native File System Architecture
